# Project architecture
- The public bot directory and moderation registration consume the browser-safe Discord command catalog, so command names, options and permission metadata stay consistent without exposing server credentials.
- Signed Discord slash commands acknowledge privately before any network work and finish via the original interaction webhook, so database/API latency cannot exceed Discord's acknowledgement deadline or expose staff errors in chat.
- Live announcement drafts are client-only Admin tools with per-account explicit browser saves and escaped HTML exports; never route them through app email sending because stream announcements are marketing.
- Discord status panels are service-only per-channel records; signed Manage Server interactions configure a validated Minecraft address, fetched only via the fixed mcsrvstat provider and refreshed by the authenticated presence keepalive without a new polling job; NULL addresses preserve legacy website panels.
- Support uses the existing private ticket and message tables and Admin ticket inbox; a dedicated authenticated submission function validates, saves and sends one fixed owner notification, while database triggers validate and rate-limit all insert paths.
- The Support Centre request cards prefill the existing supported ticket topics and subjects; published FAQ content is reused, so the presentation does not introduce parallel report or appeal storage.
- Profile appearance previews never write browser storage; only successful preference saves commit them, and profile exit restores saved appearance. Palette tokens live in global CSS and are hydrated from private account preferences on sign-in.
- Personal themes store validated hex colors in private preferences; the theme color module converts them into root CSS tokens and computes contrasting foregrounds, never accepting user CSS.
- Discord rules messages and slash-command replies share one formatter and read published website rule sections, so both channels stay consistent.

- Profile photo uploads use the existing public `plugin-screenshots` media bucket under each authenticated user ID; storage ownership rules already restrict writes to that folder, and public profile images need public URLs.
- WebM selections become a still PNG frame before upload because profile photos throughout the app are rendered as images.
- Organization membership management policies use `is_org_owner(org_id)` rather than directly reading `organizations`, so ownership checks remain valid when organization table permissions are restricted.
- Server-side notifiers call `send-app-email` with the project's own key, and that function trusts an exact match of it as well as a `service_role` JWT claim, because newer API keys are not JWTs and the JWT-only check silently rejected every bulk send.
- The existing `discord-presence-keepalive` job performs authenticated REST-only status-panel maintenance; its edge function must never open a gateway session, because minute-by-minute Identify exhausts Discord’s session-start allowance. Continuous online presence and rotating statuses require one persistent external gateway client, not serverless reconnects.
- Images the site displays are imported from `src/assets` as real files, not Lovable CDN pointer JSON, because the preview server answers `/__l5e/assets-v1/...` with the app HTML instead of the image.
- Public WardenBot status reads ongoing issues through `get_public_active_uptime_incidents` and fails closed on lookup errors, so missing outage data cannot become an operational result.
- WardenBot is a monitored service on the public status page: the uptime checker treats it as up only while Discord accepts the bot's stored credentials, because a serverless heartbeat cannot prove gateway presence, and skips the service instead of recording an outage when no token is saved.
- Per-server custom reply commands live in `discord_custom_commands` (service-role only) and are registered as Discord guild commands by REST at creation time; the interactions handler answers them only as a fallback after every built-in and admin-configured command, so a custom command can never shadow WardenBot's own commands.
- Built-in slash-command reply texts come from one shared list: defaults in `supabase/functions/_shared/discord-reply-texts.ts`, global overrides in `site_content` key `discord_command_replies` (edited in Admin → Bot → Reply texts), and per-server overrides in `discord_guild_reply_texts` (service-role only) merged last so they win. `src/lib/discord-reply-texts.ts` mirrors the defaults — keep both files in sync, and never accept arbitrary reply keys.
- External dashboards edit a server's reply texts only through the `discord-reply-texts-api` edge function, which requires the caller's own Discord OAuth token and verifies with Discord that they own or manage that exact guild before any read or write; never accept a client-supplied user or guild claim without that check.
- Per-server Welcome/Reaction Roles/AutoMod settings live in `discord_guild_module_settings` (service-role only, keyed by guild_id + module) and are edited by external dashboards only through the `discord-modules-api` edge function, which requires the `x-dashboard-secret` shared secret and verifies with Discord (bot token) that the given user ID owns or manages the given guild; AutoMod saves also sync Discord's native Auto Moderation rules so enforcement works without a gateway session.
- The signed-in member dashboard at `/dashboard` reuses the existing profile, applications, tickets, streaks and upload panels rather than adding parallel storage; `src/test/removed-routes.test.ts` lists only routes that are absent from `src/App.tsx`, so restoring a route means removing it from that list.
- Every page that renders the fixed site `Navbar` offsets its main content below the bar (`pt-24` or more), because the bar floats over the page and anything at the top — a back link, heading or button — would otherwise be clicked through to the logo or account controls.
